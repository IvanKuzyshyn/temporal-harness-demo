# Durable attachments (Task8, schema6)

## Runtime

Build the pinned helper once: `docker build -t webchat-attachment-parser:1 infra/attachment-parser` (or `docker compose --profile tools build attachment-parser`). Set **the same absolute `WEBCHAT_ATTACHMENT_ROOT`** for `web-api` and `web-worker`, e.g. `$PWD/.webchat/attachments`. The Compose `x-webchat-host-environment` mapping records this bind-directory contract for Task13's host lifecycle. It is not a container writable layer or ephemeral test directory; ordinary Compose down preserves it. No service mounts originals into the parser. Do not use/delete the legacy `.data` tree. An unset root explicitly disables upload/download and the production file adapter; no ephemeral storage fallback. Lifecycle export/setup automation belongs to Task13.

API startup recovers owned incomplete uploads before accepting HTTP. Recovery has a two-minute startup deadline and currently revalidates finalized objects; a very large corpus can require a longer operator-run recovery window. Worker startup opens the same store; it does not delete/reconcile another process's temporary objects. A cross-process advisory lock serializes upload/recovery; readers use immutable objects. Root and object filesystem permissions are0700/0600. Local OS account and Docker daemon are trusted (this remains a single-user loopback demo, not a hostile multi-tenant storage service).

## Upload/download contract

- `POST /conversations/{id}/attachments`: multipart form with **exactly one** file part named `file`, no additional parts. Binary stream ≤**1,048,576** bytes, including exact boundary acceptance; HTTP framing allowance16KiB. Filename extension and supplied file media type must agree with validated content. For browser `application/octet-stream`/omitted part type, type is selected from the allowed filename extension and then validated. Basename-only display name ≤255 UTF-8 bytes, no controls; never a storage path.
- Returns201 `{"attachment":{"id","conversationId","name","mediaType","size","checksum","status":"ready"}}` (keys shown, not literal JSON values). No original bytes, extracted text or storage paths in the response. Upload is **not** consent. Upload retries without a returned ID may create a separate object; upload itself has no request-ID/exactly-once claim.
- `GET /conversations/{id}/attachments/{attachmentId}` returns the original exact bytes only after scoped ready lookup and checksum/size verification. All originals, **including SVG and raster images**, use attachment disposition and `X-Content-Type-Options: nosniff`; Task8 exposes no inline-preview route.
- Wrong/missing conversation404; >1MiB413 `file_exceeds_1048576_bytes`; signature/format/parseability rejection422 `invalid_signature_or_unreadable_file`; missing helper/store/infrastructure503. Multipart/header errors400/415. No internal parser diagnostics in HTTP errors.
- Multiple uploads may exist independently. Admission of message/replacement permits at most **four distinct owned ready IDs**, atomically enforced by existing command validation/message joins. Staged/foreign IDs never admit. Attachment-only messages now execute.

## Filesystem protocol and recovery

`attachments.NewStore(absoluteRoot, Repository, Parser)` (`nil` parser uses the real isolated container) returns a closeable Store. `Put(ctx, ConversationID, io.Reader, UploadMetadata)` streams into a random UUID-owned directory, validates, hashes SHA256, fsyncs the immutable manifest, atomically renames `incoming` to `original`, and fsyncs the directory **before** `CreateAttachment(staged)`/`MarkAttachmentReady` commits. The key is `<random UUID>/original`, independent of filename/conversation/model input. `os.Root` confines all operations; key identity, regular file, no symlink, size and checksum are rechecked on reads.

A durable `owner.json` precedes streaming. All metadata writers (layout marker, owner, manifest) create an exclusive sibling `<final>.pending-<UUID>`, write/fsync/close it, atomically **hard-link** the final name without replacement, and fsync the containing directory before unlinking the temporary and fsyncing that directory again. This requires same-filesystem hard-link support; there is no overwrite/non-atomic fallback. An existing final identity is never replaced. The existing writer lock also covers initial marker publication; reopening a valid marker completes the root-directory fsync if its publisher died immediately after linking.

`Recover(ctx)` examines only canonical UUID directories with matching committed owner identity. New owners contain a `PublicationID` UUID identifying exactly their owner/manifest temporary names; those two names alone can be reaped after validating ownership. Older committed owners without this field still recover, but grant no temporary cleanup permission. An interrupted initial marker or owner publication leaves an unclaimed temporary (metadata only): it is ignored/preserved, not used as authority or an obstruction to later startup. No global filename-pattern cleanup occurs. A committed owner plus absent final manifest permits incomplete owned stream cleanup; a complete manifest can finalize a pre-rename object or replay failed/lost SQL writes. Unrelated files, even inside an owned directory, and finalized originals are preserved. Malformed **final** manifests/markers and checksum failures remain fail-closed; this protocol prevents new partial-final crash states rather than guessing how to repair corruption or artifacts from the old writer.

Fresh-process tests physically SIGKILL writers after temporary metadata creation/partial write, then exec independent recovery processes for initial marker, marker beside earlier originals, owner, and manifest boundaries. They verify earlier original/SQL identities and unowned files remain intact. The existing process-exit73 test after original rename/fsync but before SQL publication and the concurrent-startup regression also remain. These are process-death proofs, not simulated host/power-loss tests. The root version marker is a layout marker, never authority to delete arbitrary contents.

## Validation and bounded extraction

All original formats store unchanged: UTF-8 TXT/Markdown (reject NUL/malformed UTF-8), PDF, DOCX, PNG, JPEG, SVG. PNG/JPEG require full decode after header checks, dimension≤8192, pixels≤20,000,000. Host raster decode is bounded by these caps and the serialized upload writer. Image model resizing/payloads/children are Task9; `imageAdmissionQualified:false` is unchanged.

PDF/DOCX/SVG use Node24.21.0 and the Task1 exact packages: pdfjs-dist6.5.438, yauzl3.4.0+saxes6.0.0, resvg-js2.6.2. A separate stdin-only container is created per operation with network none, read-only filesystem, nonroot user, no capabilities, no-new-privileges,512MiB hard memory/no swap,256MiB V8 heap,1CPU,32PIDs,64FDs,8CPU-second ulimit and10-second operation deadline. The bounded client caps input/output/diagnostics and force-removes its unique named container before return. Creation joins independently of caller cancellation (still bounded10s) before removal, avoiding a late daemon-created orphan. Image pulls are disabled. A failed/timed-out create or failed cleanup propagates uncertainty and must **not** acknowledge tool-body cleanup; absence at one instant does not prove an in-flight create was joined. No host mounts, arbitrary paths, external XML entity resolver, URL-based PDF loading, scripts, macros, relationships or network fetches. Docker/image failures are explicit, never a native uncontained fallback.

- Upload validation uses `Parse(..., extract=false)`. PDF opens document/pages but never calls `getTextContent`; DOCX parses structure/ZIP/XML without collecting text; SVG static rasterization is validation, not model analysis. No extracted text is persisted on upload.
- PDF embedded text only: ≤100 pages processed, actual page count retained, explicit truncation when pages>100 or text>200,000 Unicode characters. Bundled **local standard fonts** are configured with warnings enabled; targeted Helvetica extraction asserts clean stderr and no font warning. Encrypted and image-only/empty PDFs return explicit unsupported reasons; unreadable/resource-limited extraction is an unsupported outcome, not claimed full coverage.
- PDF expanded-data protection instruments the exact pinned maintained parser's **both** JS `DecodeStream` buffer allocator and native `DecompressionStream` chunk loop with shared16MiB accounting. Build assertions fail on layout changes. This is a conservative decompressed-text/object-stream allocation cap, not a new PDF parser; decoded capacity/copies can exhaust it before16MiB logical text. Other parser/native allocations remain bounded by the container. PDF images are not rendered or OCR'd. Requalify both paths on any parser upgrade.
- DOCX uses lazy entries/strict paths/size validation; ≤1024 entries, total declared **and actual** expanded data≤16MiB, bounded XML depth64/nodes200,000/attributes64. Reads expected document text only; external relationships/macros are never followed/executed. XML DOCTYPE/undefined entities rejected. Unsupported document types and ZIP bombs fail closed. Text capped200,000 characters with explicit truncation.
- SVG accepts a deliberately narrow static subset: svg/g/path/basic shapes/title/desc and explicit numeric width/height within the same8192/20MP caps. Reject scripts, styles/CSS, images/href/use, animation, filters, text/fonts, foreignObject and external resources/entities. Resvg system fonts disabled; validation raster longest side≤2048. This intentionally rejects many otherwise valid SVGs rather than silently omitting unsafe/unsupported features. No untrusted SVG inline route or original-to-model shortcut.

## Authorization, persistence and Task9 seam

`Store.Extract(ctx, chat.ApprovalScope, AttachmentID) (chat.ExtractedDocument,error)` intentionally requires more than the brief's ID-only shorthand. The SQL repository verifies exact authorized scope, call arguments' attachment ID, immutable checksum, conversation, running turn and a registered unjoined body **before cache/byte reads**, and again on publication. New instructions still require new authorization even when parser output is cached. `ReadAttachmentExtraction` is an internal repository primitive, not an API/model preapproval path.

`NewWebAttachmentAdapter(store)` rechecks canonical arguments/action hash/toolset/version, then calls Extract behind the existing `BeginWebTool` fence. Both default activity registries retain the production safe fetch adapter when adding files. Newly attached files create deterministic step0 file actions before inference (ID/checksum/fixed extraction instruction only), so image/file consent never depends on a model guessing. Approval denial/expiry performs no extraction; only recorded outcomes enter the next model request.

Schema6 adds bounded immutable `attachments.extraction_result` JSON alongside existing extracted_text/status. `SaveAttachmentExtraction` rejects changed canonical output and records text/status/page sections/truncation atomically. A lost acknowledgment reuses the stored extraction; failed required persistence produces no success/result and retries. Parser output is content-derived, not instruction-derived. Task9 must use separate action-specific child/model analysis results, not overwrite this canonical parser cache. Images currently yield `image_analysis_not_qualified`; Task9 must choose its image path before this text-extraction primitive.

Full extracted text stays in Postgres, never workflow payloads. Tool results contain at most16,000 UTF-8 bytes plus attachment ID/page/status/truncation; model context further reduces combined excerpts to4,000 bytes with explicit truncation, within the existing12,000 input budget. Page/section offsets are Unicode-character offsets. Text is untrusted data, not executable instructions.

Ordinary completion and controlled replacement cleanup remain distinct. If Docker cannot confirm physical cleanup, the invocation stays unacknowledged and accepted controls remain blocked by the existing seal/zero barrier. An application hard-death may leave a stopped/created parser container (unique name and ownership label); do not broad-prune Docker. Operator cleanup must verify that individual owner and absence of a live client. No exactly-once physical parsing, hard-death cleanup-ack, OCR, live-model image quality, or independent-review claim.

Verification: `caffeinate -is scripts/test-web-integration.sh attachments` builds the helper and runs real isolated PostgreSQL/Temporal/API/parser/filesystem tests (inference injected), process-death recovery, approval/denial/model-request inspection and inherited cleanup/fetch regressions. All test resources are ownership-scoped; production originals and shared services are untouched.
